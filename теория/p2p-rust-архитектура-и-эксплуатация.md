# P2P по спецификации «без центра»: Rust — архитектура, структура, тесты, отладка

Документ опирается на [p2p-сеть-серверов-без-центра.md](./p2p-сеть-серверов-без-центра.md) и задаёт **инженерный каркас** для реализации на Rust: разбиение на слои, дерево модулей/крейтов, стратегии тестирования и отладки. Это не дублирование протокола, а **как уложить** его в код без смешения трёх плоскостей (§1, §11.1).

---

## 1. Принцип разбиения: три плоскости → три границы в коде

| Плоскость | Ответственность | Запрет |
|-----------|-----------------|--------|
| **Оверлей** | Транспорт, handshake, маршрутизация NodeId, PEX, repair, кэш дескрипторов, пользовательские пакеты | Не выводить глобальную политику из одного hop |
| **BFT / реестр** | Финализация команд, сертификаты высоты, Merkle root, `KEY_ROTATE` / отзыв | Не гонять полный PBFT на каждый пользовательский пакет |
| **Доверие клиента** | Якоря, мультиканальная проверка заголовков, Recovery vs авторитетность (§5.1, §11.10) | Не считать одного соседа источником истины для «текущей высоты» |

**Практика:** между слоями — **явные типы сообщений и trait-границы** (`OverlayPort`, `ConsensusPort`, `ChainSyncPort`), чтобы «удобный вызов внутрь» не смешал gossip с голосованием.

## 2. Рекомендуемая структура Cargo workspace

Вариант для роста от прототипа к продакшену (имена можно префиксовать под репозиторий, напр. `zona-`):

```
zona-p2p/                          # корень workspace
├── Cargo.toml                     # [workspace] members = [...]
│
├── crates/
│   ├── zona-p2p-types/            # NodeId, ReachSpec, слоты G/L/D, заголовки сообщений, ошибки протокола
│   ├── zona-p2p-crypto/          # ключи, подписи, хэш NodeId = H(pubkey), привязка к типам из types
│   ├── zona-p2p-transport/       # QUIC/TCP+TLS, слушатели, «два порта» оверлей/консенсус (§11.6)
│   ├── zona-p2p-overlay/         # таблица соседей, XOR/префиксный выбор next hop, PEX, repair, rate limits (§12.2)
│   ├── zona-p2p-gossip/          # ленивая репликация дескрипторов, merge правил §8.1 на локальном уровне
│   ├── zona-p2p-consensus/       # BFT: предложение блоков, голоса, сертификат (2f+1), состояние валидаторов V_e
│   ├── zona-p2p-light-client/    # проверка цепочки, fork_choice, независимые каналы (без реализации сети)
│   └── zona-p2p-node/           # сборка: runtime tokio, конфиг, wiring, metrics HTTP/Prometheus (§13.5)
│
├── crates/zona-p2p-sim/          # симуляция сети (см. §4 тестирования) — dev-dependency или отдельный member
│
├── tests/
│   └── integration/             # несколько процессов / несколько задач в одном бинарнике теста
│
└── docs/
    └── adr/                       # решения по выбору BFT (HotStuff vs Tendermint) и транспорта
```

**Почему так:**

- **`types` + `crypto`** — стабильные ABI-подобные контракты и property-тесты без сети.
- **`overlay` отдельно от `gossip`** — в спецификации разные бюджеты и семантика (маршрут vs кэш).
- **`consensus`** может подключаться позже: оверлей и лёгкий клиент тестируются с **моками** сертификатов.
- **`node`** — тонкий слой; бизнес-логика не «застревает» в `main.rs`.

Альтернатива для раннего MVP — **один крейт** с модулями `types`, `overlay`, `consensus`, … и последующий split по мере роста; границы плоскостей всё равно соблюдать через подмодули и `pub(crate)`.

## 3. Внутренняя структура ключевых крейтов

### 3.1. `zona-p2p-overlay`

```
src/
├── lib.rs
├── routing/
│   ├── xor.rs              # жадный шаг, локальные минимумы, резерв (§7.1–7.3)
│   └── prefix.rs           # опционально, §7.2
├── peers/
│   ├── table.rs            # слоты G1…Gk, L, D; referrer_id; лимиты замены за тик (§10.7)
│   ├── pex.rs              # запрос ≤q кандидатов
│   └── reputation.rs       # EWMA loss, расхождение checkpoint (§12.3)
├── repair.rs               # псевдослучайные цели от epoch_seed (§4, §5)
├── limits.rs               # find/ping/invite квоты (§12.2)
└── recovery.rs             # режим Recovery, флаги для лёгкого клиента (§5.1)
```

### 3.2. `zona-p2p-consensus` (эскиз)

```
src/
├── lib.rs
├── state_machine.rs        # применение финализированных команд к локальному снимку
├── validator_set.rs        # V_e, политика 𝒜 (читает genesis / состояние)
├── certificates.rs         # агрегация подписей, проверка кворума
└── fork_choice.rs          # §11.10, связь с genesis
```

### 3.3. `zona-p2p-node`

- Поднятие **двух** слушателей или одного мультиплексора с приоритетами (§11.6).
- Конфиг: пути к genesis, bootstrap peers, профиль CI (§13).
- **Подписка на события:** `segment_mode`, `FINALITY_PAUSED`, Recovery — для API и метрик.

## 4. Асинхронность и границы потоков

- **Tokio** — естественный выбор для множества соединений и таймеров (keep-alive, repair, эпохи).
- Разделение:
  - **один** task (или пул) на приём кадров с транспорта → декодирование → очередь в overlay;
  - **отдельный** bounded channel в consensus (backpressure = §13.2 `FLOW_CONTROLLED` на уровне узла).
- **Криптография проверки подписи** — по возможности выносить в `spawn_blocking` или пул, если профилирование покажет CPU-bound на горячем пути.

Важно: **детерминизм симуляций** (см. ниже) проще с `tokio::time::pause` и ручным продвижением времени в тестах.

## 5. Тестирование

### 5.1. Уровни

| Уровень | Что ловит | Инструменты |
|---------|-----------|-------------|
| **Unit** | XOR next hop, tie-break merge дескрипторов, лимиты PEX, формулы reputation | `#[test]`, `proptest` / `quickcheck` для NodeId и перестановок соседей |
| **Property** | «не больше одной замены G/D за тик», монотонность version при фиксированной высоте | `proptest` |
| **Component** | очередь сообщений с TTL, дедуп по `message_id`, fork двух первых hop для `critical_user` | async тесты + fake clock |
| **Integration (локальная сеть)** | несколько узлов на `127.0.0.1`, реальный handshake | отдельный `tests/*.rs`, порты из OS / фиксированный пул |
| **Simulation** | churn, partition, задержки, потери пакетов | см. §5.2 |

### 5.2. Симуляция сети

Цели из спецификации: **разреженный граф**, **churn**, **partition**, **лимиты** без поднятия сотен процессов.

Подходы:

1. **Внутренний симулятор** в `zona-p2p-sim`: абстракция `Link` с задержкой и вероятностью потери; узлы — задачи Tokio + общий «брокер» сообщений (детерминированный RNG с seed).
2. **Внешние crates** (оценить по зрелости): `turmoil` (топологии и тайминг), иногда `netsim` — сверять с версией Tokio в проекте.
3. **Нагрузочное:** крейт `dhat` / `flamegraph` для профиля; не путать с корректностью протокола.

**Инварианты для assert в симуляции:** после стабилизации — минимум два `referrer_id` где требуется §5.1; при partition — два несовместимых «хвоста» не помечаются как единый committed без `fork_choice`.

### 5.3. Контрактные / fuzz тесты

- **Fuzz декодера кадров** (`cargo fuzz` или `libfuzzer-sys`): только разбор; без сетевых сайд-эффектов.
- **Контракт между крейтами:** небольшие JSON/binary fixtures сертификатов и блоков — регресс на изменение сериализации.

### 5.4. Критерий готовности MVP оверлея

- Маршрутизация по XOR с тупиком и срабатыванием repair / второго hop.
- PEX с `q=3` и слотами G/L/D без нарушения «не все слоты от одного referrer».
- Rate limit выдаёт ожидаемые коды (`INVITE_QUOTA_EXCEEDED` и т.д.) в тестах без флаков (время через fake clock).

## 6. Отладка и наблюдаемость

### 6.1. Трассировка (`tracing`)

- **Один `trace_id` / `connection_id`** на сессию; **span** на уровне: `transport.connect`, `overlay.route`, `gossip.merge`, `consensus.vote` (если включено).
- Структурные поля: `node_id` (сокращённо), `slot`, `referrer_id`, `height`, `message_id` — по спецификации для корреляции с логами валидаторов.

Уровни:

- `DEBUG` — решения маршрутизатора (почему выбран сосед).
- `TRACE` — каждый кадр (только в dev; в проде семплирование).

### 6.2. Метрики (§12.6, §13.5)

Экспорт Prometheus/OpenTelemetry с узла:

- `overlay_messages_dropped_total{reason}`
- `bft_head_height`, расхождение с внешним наблюдателем
- `merge_queue_depth`, `segment_mode`
- EWMA loss по соседу (агрегаты, не обязательно per-peer в high-cardinality проде)

**Правило:** метрика должна иметь **понятный плейбук** (что смотреть дальше).

### 6.3. Детерминированные дампы

- Режим `ZONA_P2P_RECORD=path` — запись **всех** входящих/исходящих кадров с timestamp (монотонные) для replay.
- Режим `ZONA_P2P_REPLAY=path` — проигрывание в overlay без сети (отладка маршрута и merge).

### 6.4. Tokio Console

- Для зависаний и длинных очередей задач: `console-subscriber` в dev-сборках.

### 6.5. Сетевой уровень (вне приложения)

- `tcpdump` / Wireshark на портах оверлея и консенсуса — полезно для интеграции с внешними клиентами; **шифрование** (TLS/QUIC) ограничивает полезность без ключей сессии — закладывать **dev-only** расшифровку или подробный лог до шифрования.

### 6.6. Отладка BFT-ветвлений

- Логировать **предложение** (height, hash родителя, proposer) и **голос** с идентификатором валидатора.
- При расхождении двух наблюдателей — автоматический **снимок** известных заголовков и `referrer_id` (§12.6 триггеры).

## 7. Связь с текущим крейтом `zona`

Существующий крейт в репозитории — HTTP companion (`axum`, teach и т.д.). Рекомендации:

- **Не смешивать** HTTP API приложения и низкоуровневый P2P в одном модуле без границы: либо отдельные крейты в workspace, либо чёткий подмодуль `p2p` с зависимостью только от `node` через traits.
- Поверх P2P можно отдавать **тот же** стиль observability (`tracing`, метрики), чтобы оператор видел единую картину.

## 8. Порядок внедрения (реалистичная дорожная карта)

1. **Типы + крипто + кодирование кадров** — без сети, полное покрытие unit/property.
2. **Транспорт + handshake + подписанные дескрипторы** — один узел, один пир.
3. **Overlay: таблица слотов, XOR, PEX, repair** — симулятор с 10–50 узлов.
4. **Gossip merge** — конфликты версий и высот (мок BFT).
5. **Consensus** — подключить реальный алгоритм или заглушку с сертификатами.
6. **Light client** — мультиканальная логика против моков «лживых» пиров.
7. **Профиль CI (§13)** — сегменты, очереди слияния, метрики.

На каждом шаге — **критерии из §5–6** этого файла (тесты + метрики + сценарий отладки).

## 9. Краткий чек-лист перед релизом узла

- [ ] Три плоскости не импортируют друг друга циклически.
- [ ] Лимиты §12.2 покрыты тестами; нет «тихих» констант для продакшена без genesis.
- [ ] Recovery: узел не выдаёт авторитетный сертификат (§5.1).
- [ ] Есть сценарий partition в симуляции и документированный исход.
- [ ] `cargo test --workspace` + минимум один многопроцессный интеграционный тест на CI.
