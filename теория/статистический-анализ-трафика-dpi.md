# Статистический анализ трафика для маскировки REST-запросов под DPI

## 1. Постановка задачи

**Цель:** задать набор измеряемых характеристик сетевого обмена, при которых трафик, порождённый «маскирующей» функцией **Y(params)**, **статистически неотличим** от трафика «эталонной» функции **X(params)** с точки зрения типичных эвристик DPI и классификаторов по метаданным.

Здесь **функция** — это выполнение **REST-запроса к API**: метод, URL (включая path/query), заголовки, тело, семантика ответа. **params** — нормализованное описание одного сценария (например: размер полезной нагрузки, число заголовков, шаблон URL без секретов, код ответа, фрагментация и т.д.).

**X** — эталонный клиент или прямой обмен с API. **Y** — прокси, туннель, обёртка или альтернативный клиент, который должен сохранять бизнес-семантику, но **менять наблюдаемую статистику так мало**, что автоматическая дифференциация по трафику становится ненадёжной.

Строгое равенство распределений не требуется; требуется **отсутствие статистически значимых отличий** по выбранным метрикам при заданных уровнях значимости и мощности.

---

## 2. Что значит «Y(params) статистически равен X(params)»

Фиксируем для каждого сценария `params` две генеральные совокупности наблюдений:

- выборка от **X**: \(S_X = \{x_1, \ldots, x_n\}\)
- выборка от **Y**: \(S_Y = \{y_1, \ldots, y_n\}\)

Каждое наблюдение — вектор признаков, извлечённый из одного цикла «запрос → ответ» (и при необходимости — из связанного TLS/ TCP-поведения):

\[
z = \bigl(f_1, f_2, \ldots, f_k\bigr).
\]

**Статистическая эквивалентность** в этой модели означает:

- для каждого одномерного признака \(f_j\), важного для DPI, распределения в \(S_X\) и \(S_Y\) **не различаются** на уровне значимости \(\alpha\) (с поправкой на множественные сравнения);
- для ключевых **многомерных** проекций (например, пара «размер запроса — размер ответа») **совместные** распределения также проверяются (2D-гистограммы, энергетическая метрика, перестановочные тесты).

**Важно:** эквивалентность задаётся **относительно выбранного набора признаков**. DPI не видит «идею» API; он видит байты, тайминги и шаблоны. Поэтому набор \(f_j\) должен явно соответствовать тому, что реально измеряет классификатор (или вашему threat model).

## 3. Пространство параметров и нормализация

Перед сбором выборок **params** приводят к сравнимому виду:

| Аспект | Нормализация |
|--------|----------------|
| URL | Схема, host, шаблон path (плейсхолдеры для ID), множество имён query-ключей (без значений секретов) |
| Метод и версия HTTP | Литералы |
| Размеры | Длины тела запроса/ответа после типового сжатия на проводе (если применимо) |
| Заголовки | Множество имён; порядок; наличие стандартных полей (User-Agent, Accept, Connection…) |
| TLS | Версия, набор шифров, расширения, SNI, длины рукопожатий (если доступно в модели угрозы) |
| Время | Задержки между сегментами, RTT-прокси, длительность ответа |

Один фиксированный **params** = один сценарий; сравнение X и Y всегда **внутри одного params** (парные или стратифицированные дизайны возможны, если сеть стабильна).

## 4. Рекомендуемые измеримые характеристики (признаки)

Ниже — типичные группы признаков, по которым DPI и middlebox’ы чаще всего строят эвристики.

### 4.1. Запрос (L7)

- Размер первой линии и заголовков (байты до `\r\n\r\n`).
- Размер тела; chunked vs Content-Length.
- Число и порядок заголовков; длина значений (агрегаты, не сами секреты).
- Шаблон URL (длина path, число сегментов, наличие query).
- HTTP/1.1 vs HTTP/2: число потоков, размеры DATA-фреймов, паттерн мультиплексирования.

### 4.2. Ответ (L7)

- Класс статуса и точный код (если в threat model виден).
- Размер ответа, заголовки аналогично запросу.
- Наличие и параметры сжатия (Accept-Encoding / Content-Encoding).

### 4.3. Время и бурстность

- **TTFB**, полная длительность обмена.
- Интервалы между TCP-сегментами или между application chunks (если снимается).
- Дисперсия RTT (может отличаться у прокси).

### 4.4. TLS / транспорт (если в области анализа)

- Fingerprint клиента (JA3/JA4 и аналоги).
- Версии и suites; ALPN (h2 vs http/1.1).
- Размеры сертификатов и цепочки на проводе.

### 4.5. Связь «запрос–ответ»

- Соотношение размеров запроса и ответа.
- Условные распределения: размер ответа при фиксированном классе размера запроса.

Признаки с **низкой** чувствительностью к DPI для вашего сценария можно исключить, чтобы не раздувать множественные сравнения.

## 5. Алгоритм статистического анализа (пошагово)

### Шаг 0. Зафиксировать threat model

Определить: что видит анализатор (только домен и объёмы? полный HTTP? TLS внутри?); допустимые преобразования Y (задержки, паддинг, объединение запросов и т.д.).

### Шаг 1. Сбор данных

Для каждого интересующего **params**:

1. Выполнить **N** прогонов X и **N** прогонов Y в **схожих** сетевых условиях (время суток, маршрут; при необходимости стратификация).
2. Логировать сырые трассировки или агрегаты в безопасном виде (без секретов и ПДн в открытом виде).
3. Извлечь вектор признаков \(z\) на цикл.

Рекомендуемые минимальные порядки **N**: от нескольких десятков для грубых проверок до сотен+ для устойчивых оценок хвостов распределений.

### Шаг 2. Очистка и согласование выборок

- Отбросить явные сбои (таймауты, 5xx), либо моделировать их **отдельной** страты.
- Убедиться, что сравниваются одинаковые **params** (тот же шаблон запроса и ожидаемый класс ответа).

### Шаг 3. Описательная статистика

Для каждого признака \(f_j\) и каждой выборки: медиана, квартили, среднее (если уместно), размах, оценка плотности (KDE), доли в бинах для дискретных величин.

### Шаг 4. Проверка одномерных распределений

Подбирать тест по типу данных:

| Тип | Примеры тестов |
|-----|----------------|
| Непрерывные, незаданное распределение | Двухвыборочный **Кolmогорова–Смирнова**, **Cramér–von Mises**, перестановочный тест по медиане/среднему |
| Дискретные / категориальные | **χ²** по таблицам сопряжённости, **G-тест** |
| Зависимые пары (редко) | Парный знаковый ранг Вилкоксона |

Уровень значимости по умолчанию: \(\alpha = 0.05\), с **поправкой** (Бонферрони или FDR Benjamini–Hochberg) на число признаков \(k\).

**Критерий прохождения:** нет значимого отличия по \(f_j\) после поправки **или** отличие укладывается в заранее заданный **практический порог эффекта** (например, разница медиан размеров не более δ байт — задаётся предметно).

### Шаг 5. Многомерная сходимость

- Для пар (например, размер запроса × размер ответа): сравнить 2D-гистограммы (**χ²** после биннинга) или **energy distance** между выборками.
- При умеренной размерности — **перестановочный** тест по произвольной метрике (MMD с RBF-ядром и т.п.) на пилотных данных.

### Шаг 6. Сводный критерий для Y(params)

Для фиксированного **params** объявляем Y **статистически эквивалентным** X, если:

1. все **обязательные** (в threat model) признаки прошли шаги 4–5;
2. нет провалов по **критичным** дискретным атрибутам (версия TLS, ALPN, HTTP-версия), если они наблюдаемы;
3. временные метрики не создают отделяемого кластера (визуально и/или тестом).

### Шаг 7. Обобщение на семейство сценариев

Повторить для **решётки params** (разные методы, размеры тел, коды ответов). Итог — карта «params → пройден/не пройден» и список узких мест (какие \(f_j\) ломают эквивалентность).

### Шаг 8. Итерации над Y

На основе провалов настроить Y: паддинг тел и заголовков, выравнивание таймингов, согласование HTTP/2-паттернов, клиентский TLS-стек и т.д.; повторить сбор до достижения критериев или до упора в ограничения протокола.

---

## 6. Ограничения метода

- **Условность набора признаков:** реальный DPI может использовать признаки, не входящие в ваш список — тогда эквивалентность «в модели» не гарантирует необнаружимость в поле.
- **Смена контекста:** маршрут, CDN, нагрузка сервера меняют распределения; нужны повторные измерения.
- **Этика и право:** маскировка трафика может нарушать политики сетей и законодательство; документ описывает **методологию анализа**, а не поощрение конкретного использования.

## 7. Краткая сводка

| Этап | Содержание |
|------|------------|
| Нормализация | Сопоставимые **params** и безопасные логи |
| Признаки | Размеры, заголовки, шаблоны URL, тайминги, TLS/HTTP2 при необходимости |
| Сравнение | Одномерные тесты + многомерные проверки, поправка на множественность |
| Вердикт | Y(params) ≈ X(params), если обязательные метрики неразличимы статистически и по практическим порогам |

Так задаётся воспроизводимая процедура: от **сравнения REST как функций от params** к **проверяем гипотезам о совпадении наблюдаемых распределений** тех аспектов трафика, по которым работает DPI.
